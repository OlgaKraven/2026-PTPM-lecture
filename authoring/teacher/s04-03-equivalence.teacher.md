<a id="s04-03-equivalence-s004"></a>

### 4. Разбиение опирается на правило обработки

Класс эквивалентности объединяет значения, для которых ожидается одинаковая обработка по выбранному признаку. Представитель проверяет этот признак у класса. Разбиение — обоснованная гипотеза о поведении, а не доказательство одинаковости реализации на каждом входе.

Если доставка 300 рублей для всех сумм меньше порога, мы выделяем такой класс по одному правилу результата. Внутри него ещё могут оказаться дефекты переполнения или особого нулевого значения. Метод сокращает число проверок при выбранной модели, а не освобождает от проверки рисков. Классы могут относиться не только к числам: это также типы файлов, состояния или категории пользователей.

**Запишите.** Класс эквивалентности — часть области данных, элементы которой предположительно обрабатываются одинаковым образом в рамках выбранного условия.

### 5. Классы учебного тарифа

Учебный контракт принимает только type(amount) is int; bool и None относятся к K4.

| Класс | Область | Ожидаемое поведение |
| --- | --- | --- |
| K1 | Целые числа 0…2999 | Вернуть 300 рублей |
| K2 | Целые числа ≥3000 | Вернуть 0 рублей |
| K3 | Отрицательные целые | ValueError |
| K4 | Значения другого типа | TypeError |

Сначала фиксируем универсум: рассматриваем передаваемые значения Python. Допустимы именно целые суммы. Логическое True в Python связано с целыми числами, но наш контракт его запрещает явно. Для K4 правило обработки одинаково по типу исключения, однако конкретные представления вроде пустой строки и None могут вызывать разные дефекты; их можно выделить в подклассы для отдельного риска.

### 6. Проверьте полноту и отсутствие пересечений

Каждый рассматриваемый вход должен попасть в определённую часть разбиения. Формулировки «до 3000» и «от 3000» требуют уточнения включения границы. Недопустимый тип нужно отделить от недопустимого значения правильного типа.

Запишем два класса как 0≤amount≤3000 и amount≥3000: значение 3000 попало в оба. Другой вариант — amount<3000 и amount>3000 — потерял сам порог. Таблица должна исключать такую неоднозначность. Для строк правило сравнения диапазонов вообще неприменимо до проверки типа; нельзя относить строку минус один в класс отрицательных целых.

**Запишите.** Для выбранного условия классы разбиения не пересекаются и покрывают рассматриваемую область.

### 10. Минимальный набор представителей

### 11. Лишние похожие значения могут не расширять охват

1500, 1600 и 1700 принадлежат одному классу тарифа. Они полезны для иных рисков только при отдельном обосновании. Если цель — охватить правила бесплатной и платной доставки, нужно добавить представитель класса от 3000.

Не путайте избыточность относительно одного признака с абсолютной бесполезностью. Несколько входов внутри класса могут выявить случайные особенности реализации. Но нельзя говорить, что три близких числа охватили три тарифных правила, когда правило одно. В протоколе указываем, какую гипотезу проверяет добавленное значение; это помогает распределить ограниченное время.

**Запишите.** Охват классов оценивают по представленным частям разбиения, а не по общему числу тестовых значений.

### 12. Вход и ожидаемое исключение

Ноль, пустая строка и отсутствие значения не взаимозаменяемы.

| Переданное значение | Принадлежность | Ожидается |
| --- | --- | --- |
| 0 | Допустимый целый, платная доставка | 300 |
| −1 | Недопустимое целое | ValueError |
| "" | Пустая строка, неверный тип | TypeError |
| None | Отсутствие значения, неверный тип | TypeError |

Все три значения иногда неформально называют «пустыми», но у них разный смысл. Ноль является допустимой суммой по контракту. Пустая строка вообще не число. None — отдельный объект, обозначающий отсутствие значения в этом учебном интерфейсе. Если бездумно использовать проверку if not amount, эти случаи смешаются и корректный ноль может быть отвергнут.

### 16. Одна недопустимость за один случай

Если проверяется отклонение неправильного количества, цену задают допустимой. Два неверных входа могут привести к ранней ошибке одного параметра и скрыть отсутствие проверки другого. Это не запрещает комбинированные сценарии, но меняет их цель.

Пусть функция принимает count и price. На count=−1, price="abc" программа может сразу отклонить строку цены, даже если количество вообще не проверяется. Такой успешный отказ ничего не говорит о защите количества. Поэтому сначала тестируем count с нормальной ценой, затем тип цены с нормальным количеством. Позже добавляем сочетания, если порядок проверки или общая ошибка входят в контракт.

**Запишите.** Для проверки отдельного недопустимого класса остальные параметры выбирают допустимыми, чтобы не маскировать проверяемое условие.

<a id="s04-03-equivalence-s017"></a>

### 17. Изолированные проверки total(count, price)

Учебные правила: count — целое 1…10; price — целое ≥0; неверный диапазон даёт ValueError, тип — TypeError.

| Количество | Цена, руб. | Цель |
| --- | --- | --- |
| 2 | 100 | Допустимое вычисление 200 |
| −1 | 100 | Отклонение неверного количества |
| 2 | "100" | Отклонение неверного типа цены |
| 0 | 100 | Отдельное правило для нуля |

В последней строке ноль количества недопустим, потому что таков контракт total. Не переносим сюда разрешение нулевой суммы доставки из другого модуля. Разбиение всегда привязано к конкретному входу и правилу. Для обычного расчёта 2×100 равно 200; для неверного count тип price остаётся допустимым, что позволяет наблюдать именно проверку количества.
