### 4. Модульный тест автоматизирует сравнение

Модульный тест проверяет поведение небольшой части программы. Он создаёт нужные условия, вызывает проверяемый код и сравнивает наблюдение с ожиданием. Наличие тестового файла само по себе не подтверждает качество проверки.

Мы уже умеем выбирать вход 3000 и ожидание ноль. Теперь выражаем этот же замысел кодом. Автоматизация сохраняет повторяемость сравнения и позволяет быстро запустить набор после изменения. Она не выбирает правильный контракт за разработчика. Если ожидание переписано из дефектной реализации, автоматический тест будет столь же слабым, как ручная проверка с неверным эталоном.

**Запишите.** Модульный тест — автоматизированная проверка поведения ограниченной единицы программы в контролируемых условиях.

<a id="s05-01-unit-tests-s005"></a>

### 5. Подготовка → действие → проверка

```python
import unittest
from delivery import delivery_fee

class DeliveryTests(unittest.TestCase):
    def test_threshold_is_free(self):
        amount = 3000
        actual = delivery_fee(amount)
        self.assertEqual(actual, 0)
```

Python 3; delivery.py и test_delivery.py расположены в одной папке.

amount задаёт данные подготовки. Вызов delivery_fee — действие. assertEqual сравнивает фактический результат с ожидаемым нулём. При расхождении unittest зарегистрирует неуспех и продолжит остальные независимые тесты. Ожидаемое число не вычисляется повторным вызовом той же функции: оно получено из правила тарифа. Имя метода начинается с test, чтобы стандартный загрузчик нашёл его.

### 6. Ручной случай и исполняемый тест

Запуск из папки examples: python -m unittest discover -v

| Данные | Сумма 3000 рублей | amount = 3000 |

Если запуск сообщает ноль тестов, отсутствие падений не доказывает прохождение нашего случая. В учебном комплекте есть готовые файлы, поэтому студент может воспроизвести этот маршрут после занятия.

### 10. Связанный набор граничных случаев

```python
def test_threshold_neighbours(self):
    for amount, expected in [(2999, 300),
                             (3000, 0),
                             (3001, 0)]:
        with self.subTest(amount=amount):
            self.assertEqual(
                delivery_fee(amount), expected)
```

Метод находится внутри DeliveryTests; subTest сохраняет имя входа при расхождении.

Все три строки проверяют одно тарифное правило возле одного порога. subTest отделяет результаты по входам и помогает не остановить весь цикл после первого расхождения. Если внутри одного цикла оказались доставка, запись в базу и изменение пользователя, общая тема потеряна. Здесь группировка обоснована одной моделью и одинаковой формой утверждения.

<a id="s05-01-unit-tests-s011"></a>

### 11. Исключение — ожидаемый результат

```python
def test_negative_is_rejected(self):
    with self.assertRaises(ValueError):
        delivery_fee(-1)

def test_string_is_rejected(self):
    with self.assertRaises(TypeError):
        delivery_fee("3000")
```

Оба метода находятся в DeliveryTests. Проверяемый вызов расположен внутри контекста assertRaises.

В первом тесте мы ожидаем конкретный тип исключения. Если исключения не будет, тест завершится расхождением; если возникнет другой тип, он будет ошибкой выполнения теста. Нельзя помещать вызов перед with: тогда контекст не сможет его проверить. Не ловите всё через except Exception: это способно принять посторонний сбой за правильное отклонение данных.

<a id="s05-01-unit-tests-s012"></a>

### 12. Один тест — одна проверяемая ситуация

Разделяйте независимые причины падения: порог тарифа, неверный тип и отрицательная сумма заслуживают отдельных имён. Несколько утверждений допустимы, если вместе описывают одно поведение: например, сигнал отказа и неизменность состояния.

Абсолютный запрет второго утверждения вынуждает повторять одинаковую подготовку или скрывает часть контракта. Противоположная крайность — один огромный тест всей системы: при первом расхождении остальная часть не выполняется. Ищем границу по поведению. Для отказа резервирования утверждения False и прежний остаток связаны; проверка другого независимого отчёта уже должна жить отдельно.

**Запишите.** Единство теста определяется одной проверяемой ситуацией и понятной причиной неуспеха; количество assert само по себе не является критерием.

### 16. Объект начинает каждый тест с известных данных

У класса результат проявляется в возвращаемом значении и состоянии. Для независимых случаев создают отдельные объекты. Скрытая зависимость от предыдущего теста делает результат чувствительным к порядку запуска.

В unittest setUp вызывается перед каждым тестовым методом, если он определён. Но для двух коротких тестов новый Cart можно создать прямо в каждом методе: это яснее и не требует лишней абстракции. Общий объект на уровне модуля нежелателен, если тесты его меняют. Один запуск может пройти, а смена порядка создаст непонятное падение.

**Запишите.** Тестовая фикстура — подготовленные данные, объекты и условия, необходимые для выполнения теста.

### 17. Успешное резервирование

```python
from inventory import Cart

def test_reserve_changes_stock(self):
    cart = Cart(stock=6)
    accepted = cart.reserve(2)
    self.assertTrue(accepted)
    self.assertEqual(cart.stock, 4)
```

Метод внутри unittest.TestCase; оба assert описывают успешный резерв 2 единиц.

Создали новый объект с шестью единицами. reserve должен вернуть истину и оставить четыре. Если убрать второе утверждение, дефектный метод с постоянным True пройдёт. Если убрать первое, метод может корректно изменить остаток, но вернуть неверный сигнал вызывающему коду. Эти наблюдения связаны одним контрактом операции.

<a id="s05-01-unit-tests-s018"></a>

### 18. Отклонённый запрос не меняет остаток

```python
def test_insufficient_stock_is_unchanged(self):
    cart = Cart(stock=4)
    accepted = cart.reserve(5)
    self.assertFalse(accepted)
    self.assertEqual(cart.stock, 4)
```

Новый объект отделяет случай отказа от предшествующих успешных операций.

Это другая проверяемая ситуация, поэтому отдельное имя. Ожидание остатка равно исходным четырём, а не минус одному. Сравнение состояния берётся из контракта отказа. Если метод вначале вычитает, а затем решает вернуть False, этот тест обнаружит дефект. Здесь не требуется база данных: объект полностью контролируется в памяти.
