### 4. Набор собирают из независимых проверок

Файл test_delivery.py содержит тарифные случаи, test_inventory.py — резервирование. Каждый класс наследует TestCase, методы начинаются с test. Если файл переименовать в delivery_checks.py, стандартный discover может его не найти. Поэтому сначала проверяем состав найденного набора. Количество тестов является индикатором состава, но не заменяет просмотр конкретных имён и целей.

**Запишите.** Набор тестов — совокупность тестов, организованных для совместного выполнения и оценки результатов.

Первый вариант ищет весь комплект. Второй удобен при работе над модулем. Третий помогает исследовать конкретный дефект, но не подменяет общий прогон после исправления. У команды обнаружения есть рабочая папка: запуск уровнем выше без настройки пути может найти другой состав. Сохраняем команду и её рабочий каталог в техническом протоколе.

<a id="s05-03-suite-quality-s006"></a>

### 6. Почему «OK» может быть недостаточно

Обнаружение — отдельная часть маршрута. Ноль ошибок при нуле запусков не является свидетельством поведения. Даже большой набор может потерять один критичный файл, поэтому при изменениях имен полезно сверять список. Не назначаем произвольное минимальное число как универсальный критерий качества: важно, какие требования и риски представлены.

<a id="s05-03-suite-quality-s010"></a>

### 10. Основные исходы unittest

Категория помогает начать диагностику, но не назначает виновника. FAIL может происходить из неверного ожидания. ERROR может быть следствием реального дефекта модуля или ошибки подготовки. При assertRaises отсутствие ожидаемого исключения даст FAIL, а исключение другого типа обычно ERROR. Поэтому читаем не только итоговый счётчик, но и имя случая, traceback и текст утверждения.

<a id="s05-03-suite-quality-s011"></a>

### 11. Пример отчёта о расхождении

Имя показывает правило порога. Строка сравнения сообщает фактическое 300 и ожидаемое ноль, если аргументы assertEqual были переданы в таком порядке. По ней нельзя узнать вход, поэтому открываем конкретный тест. Итог подтверждает двенадцать выполненных методов с одним неуспехом; он не показывает, сколько различных требований охвачено и какие subTest были внутри.

<a id="s05-03-suite-quality-s012"></a>

### 12. Отчёт связывают с условиями запуска

Девяносто девять успешных проверок не отменяют одну, которая обнаружила неверный итог оплаты. Важно содержание. При сравнении двух прогонов сверяем также состав: исчезнувший тест может создать ложное улучшение. Данные окружения не размещают на учебной обложке; они нужны в протоколе для воспроизведения конкретного технического результата.

**Запишите.** Отчёт о прогоне — запись состава, условий и исходов конкретного запуска набора тестов.

### 16. Тест, проходящий при неверной доставке

Свойство неотрицательности может быть полезным отдельным инвариантом. Но оно недостаточно для правила бесплатности. Не объявляем любой тест свойства плохим; оцениваем его относительно заявленной цели. Если тест называется проверкой порога, он должен различать ноль и 300. Исправление — точное assertEqual для порога, дополненное другими выбранными входами.

**Подготовка.** Открыть учебные файлы examples. Python 3; стандартная библиотека unittest. Для фрагмента метода использовать класс TestCase, указанный на слайде.

<a id="s05-03-suite-quality-s017"></a>

### 17. Контролируемое нарушение проверяет чувствительность

Мы выполняем ручной учебный опыт, а не строим полный инструмент мутационного тестирования. Прошедшая мутация требует разбирательства: тест мог не покрыть нужный вход, ожидание могло быть слабым, либо изменение вообще не влияет на наблюдаемое поведение при данных требованиях. Не каждое изменение обязано породить новый отказ; эквивалентные варианты возможны.

**Запишите.** Мутационное тестирование оценивает набор через небольшие изменения программы и способность тестов обнаружить их.

<a id="s05-03-suite-quality-s018"></a>

### 18. Какой вход различит реализации

Последняя строка показывает, что даже точное равенство может не помочь на неудачном входе: два плюс два и два умножить на два равны четырём. Поэтому качество теста складывается из выбора данных и силы ожидания. Для порога нужен ровно 3000; для состояния — наблюдение stock; для арифметики — различающие числа.

**Подготовка.** Оставить время на самостоятельную запись решения; полный ответ показать после попытки.

**Вопрос или задание.** Контракт multiply(a,b): произведение двух целых. Единственный тест assertEqual(multiply(2,2),4). Изменённый код возвращает a+b и тест проходит. Предложите новый вход с точным ожиданием, объясните различие и опишите безопасное завершение опыта.

**Ответ после попытки.** Например a=3,b=5: произведение 15, сумма 8. Добавить assertEqual(multiply(3,5),15); на изменённом коде он должен упасть. Восстановить умножение и повторить весь набор. Изменения делать в учебной копии; намеренно сломанный код не включать как исправную реализацию.
